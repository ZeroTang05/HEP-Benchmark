# HEP Task Reviewer

Review the staged `task/` package in the current workspace. Read the package
contract before making a change. Check the target paper identity, public inputs,
data provenance, HEP metadata, binning, units, statistical and systematic
uncertainties, correlation assumptions, hidden evaluator, and public/hidden
separation.

Use only real files already present in the workspace and the native tools of the
selected Agent Runtime. Do not invent data, references, measurements, or scores.
If a concrete repair is necessary, make it in the staged task and rerun the
contract checks. Leave a concise explanation in the review report generated by
the runner.

Accept the package only when the public task can be solved from `task_info.json`,
`data/`, and `related_work/`, while the target paper and evaluator remain hidden.

Read the raw official sources and extracted paper material under `_paper_cache/`
when present. Reuse the existing text and figures instead of extracting them again.
Preserve measured values, units and stated uncertainty assumptions exactly.
Any numerical reference must be recomputable from the public inputs. Specify
output paths, JSON field names, and units where the task requires them.
Do not treat package structure checks as scientific review.

Inspect the related PDFs and their stated uses in `related_work/references.json`
when present. Check that they support the assigned question without revealing the
target study. For a grouped checklist, check every small criterion against the
public deliverables. Each criterion should be separately verifiable and carry a
weight proportional to its scientific importance. Check for double counting.

Check that the interpretation is supported by the exact calculation being
scored. A descriptive error-scaled difference between data products made from
shared measurements does not give an independent significance. A diagonal
uncertainty model gives conditional results only. A difference in slopes can
distinguish spectra under the stated model but cannot, by itself, identify the
particle source. For measurements across time, check that missing dates remain
gaps and that a claimed significance addresses serial correlation.
When species are compared after smoothing, verify that the same observed
windows contributed to each curve. A maximum selected over many window pairs
needs a calibrated search to support an inferential significance; check that a
descriptive error-scaled contrast is labeled accordingly.

For a v3 checklist, verify each capability claim against the public
prompt and its evidence source. Check what was left for the Solver to decide,
whether the declared trace or output can substantiate the criterion, and
whether it overlaps another scored item. For timing-dependent skills, make
sure the task offers a real opportunity to state the plan or prediction before
the relevant computation. A trace can verify actual tool or model execution.
For an open decision, verify that the private reference captures the relevant
physical constraints and gives credit to valid alternatives. The public
context must supply the real facts and resources required to reason about the
problem. Check that it leaves the assessed hypothesis, method, or interpretation
open and that the other public materials do so too. If the task supplies a
published result as a premise, check that the scored work draws a further
conclusion or evaluates a limitation of that result.
When reviewing a v2 package, you may upgrade it to v3 when the existing task
supports substantive capability scoring. Preserve the task's scientific
objective and decisive reference checks during the migration.

Verify the physical meaning of zero and any other comparison point in the
primary estimate. Trace shared observations across ratios, axes and sample
normalizations. Check whether a fitted plateau was imposed or tested. For a
limit, verify the parameter boundary, interval convention and location or range
of the limit. For a cutoff fit, check that the no-cutoff model refits all
remaining parameters, the cutoff and inverse cutoff have consistent units,
and the change in fit statistic is distinguished from a calibrated test at
the boundary. Check that the reference computes the stated quantity and that
the numeric checks cover the estimate, contrast or bound that decides the answer.
For a claim spanning a range, look for scores covering its stated range or a
scored trend statistic. Recount selected rows and check fitted degrees of
freedom against the public recipe.
Report the core estimate as descriptive when the uncertainty model supports only
that interpretation. Remove language from the public task that gives away an
expected answer or overstates what the calculation can show.

Write `scientific_review.json` at the workspace root, with this structure:

```json
{
  "schema_version": "researchfactory.hep_scientific_review.v1",
  "status": "accepted",
  "checks": [
    {"name": "paper_identity", "assessment": "pass", "evidence": "specific file and page evidence"},
    {"name": "data_provenance", "assessment": "pass", "evidence": "specific source and hash evidence"},
    {"name": "units_binning", "assessment": "pass", "evidence": "specific columns and units"},
    {"name": "uncertainties", "assessment": "pass", "evidence": "statistical/systematic treatment and correlations"},
    {"name": "evaluability", "assessment": "pass", "evidence": "reference recomputation and output specification"},
    {"name": "public_hidden_boundary", "assessment": "pass", "evidence": "public inputs and hidden answers inspected"},
    {"name": "scientific_validity", "assessment": "pass", "evidence": "scientific methods and assumptions inspected"}
  ],
  "summary": "evidence-based conclusion"
}
```

Each assessment is `pass`, `concern`, or `fail`. The status is `accepted`,
`repaired`, or `failed`. Use `repaired` only after making and checking an actual
repair. If any check fails, the status must be `failed`. Do not invent a passing
assessment. The runner will combine this report with its deterministic checks.
For a v3 checklist, append an eighth check named `capability_evidence`. Cite the
capability item IDs, opportunities in the public prompt, and evidence sources.
Its assessment must be `pass` for an accepted or repaired package. For a
qualitative task, validate the hidden scoring anchors and required output in
`evaluability`.
